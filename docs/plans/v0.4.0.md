# EMURU v0.4.0 implementation plan

**Goal:** move operation from systemd to operator-controlled Docker Compose while preserving v0.3.4 inference, qualification, security and Telegram contracts. This plan is the source of truth for v0.4.0 scope and acceptance. See [architecture](../ARCHITECTURE.md) for existing module ownership and invariants; this plan does not restate them.

**Baseline:** v0.3.4, commit `5a2f09a7e9a57da2e6f59ccc238b639112779f21`.

## A. Docker lifecycle and readiness

Extend `scripts/hermes/container.py`; make `scripts/service/wake.sh` the operator entry point. Separate one-time initialization from routine startup so wake never rewrites private deployment state. Serialize lifecycle operations and reject Docker startup while the systemd poller is active.

Start inference infrastructure first. Before enabling Telegram intake, verify authenticated LiteLLM access, selected model availability, route/profile/vault bindings and qualification state through existing checks. Start the guarded Telegram worker only after these checks; report success only after its current READY checkpoint. Keep explicit model selection and existing primary/local attempt policy.

**Acceptance:** failed checks never start intake; READY means gateway and guarded worker checks passed in this startup. Repeated wake preserves configuration and cannot create a second poller. No model downloads occur.

## B. Shutdown, status and Telegram reliability

Extend the existing worker/native shutdown path and service scripts. Stop polling and new claims first; allow the active owner turn to finish within its existing 600-second deadline, then stop the worker before inference services. Set Compose `stop_grace_period` to 660 seconds for the maximum turn plus bounded cleanup. Forced termination records uncertainty and never replays the action. Preserve queue and native receipts.

Make `status.sh` strictly read-only. Report sanitized queue counts, health and observations; bind observations to timestamp and deployment/container identity so stale data cannot be reported as current. Report last-used route separately. Use these operational states:

- `READY`: fresh guarded worker and primary readiness.
- `DEGRADED_PRIMARY`: primary unavailable; qualified local route is usable.
- `LOCAL_UNQUALIFIED`: primary usable; local qualification is absent or invalid.
- `UNAVAILABLE`: known blocking failure or no usable route.
- `STOPPED`: Compose deployment confirmed stopped.
- `UNKNOWN`: evidence is missing, stale or inconclusive.

Keep owner-only intake, final-response-only delivery, five constrained vault tools, durable admission, duplicate-dispatch safeguards, inference deadlines, context admission, streaming boundaries and no-replay semantics.

**Acceptance:** shutdown order is intake, worker, inference. Graceful and forced shutdown preserve receipts and never replay uncertain work. Status performs no initialization, queue recovery, pruning, mutation or inference request; stale observations yield `UNKNOWN`.

## C. Automated regression and CI coverage

Extend existing lifecycle, Telegram, gateway and disposable Compose tests, then add the checks to `.github/workflows/ci.yml`. Cover clean startup, shutdown ordering, recreation, SIGTERM, forced termination, host-reboot recovery, duplicate launch, primary/local outages, pending receipts and uncertain actions. Assert owner-only and final-only delivery, five vault tools, one primary plus at most one qualified-local attempt, state continuity, read-only status, `restart: "no"`, private networking and secret isolation.

Use synthetic backends and shortened test deadlines; separately assert the production 600-second turn bound and 660-second Compose grace. CI and live qualification are separate evidence. CI must not use production credentials, qualify real hardware or download model weights.

**Acceptance:** CI, focused regressions and the disposable Docker acceptance pass. SIGTERM and forced-stop tests confirm no replay. Host reboot is simulated in CI and verified on the target host before release.

**Commands:**

```bash
uv run --frozen pytest -q
uv run --frozen ruff check .
uv run --frozen ruff format --check .
uv run --frozen python scripts/hermes/container-check.py --config-only
uv run --frozen python scripts/hermes/container-check.py
```

The full container check requires Docker and pinned images; it uses disposable credentials and a synthetic upstream. Run focused tests by their affected paths during development.

## D. Documentation, migration and release preparation

Update README, runbook, CI/release evidence and service scripts to describe Compose as the normal operator workflow. Keep the systemd unit and installation intact until cutover acceptance passes. Document rollback as a transfer of the latest stopped state; never restore an older queue over newer receipts.

Migration checkpoints, in order:

1. Pass CI and disposable Docker acceptance; verify target-host live qualification separately.
2. Initialize and validate Docker deployment without starting its Telegram poller.
3. Stop old intake; confirm systemd process exit and lock release. Back up stopped profile, queue, native receipts and required bindings together.
4. Transfer current state and verify owner, bot, permissions, vault binding and receipt continuity before starting Docker intake.
5. Prove READY, read-only Telegram retrieval, eligible qualified-local fallback and primary recovery. Record host reboot and shutdown evidence.
6. Only after these checks pass, disable and retire the installed systemd user service. For rollback, stop Docker first and carry the newest receipts back before restarting systemd.

**Acceptance:** operator can follow migration and rollback without concurrent pollers or receipt rollback. Release evidence records commit and image identities, CI results, live qualification, Telegram checks, reboot result and migration checkpoints separately. No production cutover occurs as part of CI.

## Safety boundaries

No new router, queue, scheduler, database, supervision framework, infrastructure, vault tools or write permissions. No public inference ports, automatic model downloads, weakened authentication or automatic replay. Keep the existing LiteLLM gateway and v0.3.4 routing contracts. Do not stop or retire the production systemd service until the ordered migration checkpoints pass.
