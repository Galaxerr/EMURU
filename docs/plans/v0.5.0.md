## 2. Architecture and reuse decision

Extend EMURU’s existing MCP backend as the sole agent vault mutation authority. Keep the Telegram adapter and Hermes pin.

Verified local Hermes checkout is clean and matches 7157422022ff06f3e632d1dd394ee1253b17ad37, recorded as v0.21.5.

| Candidate | Verified capability | Decision |
|---|---|---|
| Native filesystem and Obsidian skill | Reads, searches, writes and patches; file tools include stale-write checks and internal locks | Reject as mutation authority. No EMURU root policy, durable mutation receipts or Obsidian-wide lock |
| Native skills | Available; Obsidian skill calls filesystem tools and sometimes terminal | Adapt workflow guidance only; keep generic skills/filesystem/terminal toolsets disabled |
| Existing editable MCP connector | Create, update, exact replacement and move; change checks and atomic replacement | Reject integration for v0.5.0; requires substantial policy and recovery adaptation |
| Native Telegram | Persistent history and bounded completed-update receipts | Retain current adapter. Native receipts lack EMURU’s durable queued admission and cross-process guarantees |
| Todo / Kanban | Session-oriented Todo; durable SQLite Kanban with workers and dependencies | Keep disabled. Project tasks remain Markdown; execution boards belong to v0.6.0 |
| Delegation / cron | Present in pinned runtime | Keep disabled; outside scope |

The connector documents mcp<2, whereas EMURU uses MCP 2.x in its separate environment. It also leaves live Hermes verification pending. Its default bookkeeping and optional post-write commands add unwanted effects. Connector documentation

Current connector source checks for changed text before replacement, but does not provide EMURU’s approved-root policy or durable operation protocol. A check followed by replacement still needs cooperating writers. Connector source

Decisions already selected

- One shared local vault; no Git/Syncthing synchronization implementation.
- Exclusive edit windows: pause Obsidian and other writers during application.
- Preview and owner approval for every broader mutation.
- Goals, tasks, decisions and results inside each project note, using stable Obsidian block links.

Authority and interfaces

- Keep existing read/search tools. Add a full-content revision hash to vault_open.
- Preserve Inbox capture through vault_write, routing it through the same hardened writer.
- Add vault_propose for approved-root creation and exact anchored updates. It persists a proposal; it cannot apply it.
- Add owner-only /apply <proposal-id> and /cancel <proposal-id> transport commands. Application bypasses the model and invokes the guarded backend through an internal operator entrypoint.
- Approval binds the exact proposal, target vault and expected revision. Any changed proposal requires new approval.
- Store proposals and mutation receipts in a private SQLite file under the existing persistent profile. This is recovery metadata, not another task or memory database.
- Keep broader writes disabled by default. Approval of this plan authorizes synthetic implementation only.

## 3. Ordered milestones

### v0.4.1 — Write boundary and recovery prerequisites

Behavior: Establish default-deny policy, shared serialization and recoverable operational state before exposing broader writes.

Components: Reuse vault/target.py, profile validation, service lifecycle and runbook backup procedure (docs/RUNBOOK.md). Add vault/mutations.py and focused mutation/recovery tests. No new dependency.

Decisions:

- Private policy explicitly allows selected locations under 10_Projects, 20_Areas and 30_Resources. Inbox remains capture staging.
- Deny private, unknown, journal/archive and generated locations for agent mutations. Generated indexes retain their existing internal authority.
- Use descriptor-relative traversal with no-follow checks, regular-file validation and a common interprocess lock. Cover parent directories, destination and temporary files.
- Reject symlinks, hard-linked mutation targets, traversal and special files.
- Journal proposal identity, payload digest, target, before/after hashes and outcome. Retain mutation receipts independently of Telegram pruning.
- Reuse stopped tar backups and checksums. Include vault, profile/history, queue sidecars, mutation state, route configuration and deployment identities.

Acceptance/tests: Synthetic allowlist and escape tests; competing-process exclusion; malformed policy fails closed; stopped backup restores into another directory with receipt/history continuity. Manual disposable restore inspection confirms permissions and checksums.

Risks/gates: Filesystem locks do not constrain Obsidian. Exclusive windows are an operating requirement. Real backup proof and unresolved state reconciliation block activation, not this milestone.

### v0.4.2 — Guarded creation, updates and crash recovery

Behavior: Create approved notes and apply precise updates without rewriting unrelated bytes.

Components: Modify vault/mcp.py, vault/indexer.py, scripts/hermes/vault.py and the v0.4.1 writer. Extend vault unit and stdio integration tests.

Decisions:

- One note per proposal. No arbitrary delete, rename or multi-file transaction.
- Creation requires an absent destination; never invent numbered filenames after collisions.
- Updates require a full-file revision and unique exact anchors. Preserve untouched frontmatter, formatting, links and summaries byte-for-byte.
- Reject stale revisions, ambiguous anchors and unresolved merge markers. Re-read and prepare a new proposal; never auto-merge.
- Persist intent before publication. Stage and fsync content, publish atomically, fsync the directory, then record completion.
- Index failure after publication reports “saved; indexing pending.” Never delete a committed note to roll back a derived index failure.
- Recovery compares recorded hashes with disk. Recognize completed effects; quarantine indeterminate effects. Never automatically reapply a prepared mutation.
- Repeating an applied proposal returns its receipt without writing again.

Acceptance/tests: Preserve unrelated human edits made before proposal creation; reject edits made after preview; concurrent apply commits once. Inject crashes before/after publication and receipt commit, plus disk-full and index failures. Manual synthetic preview/apply/readback smoke test.

Risks/gates: An editor violating the exclusive window can still race filesystem replacement. Activation requires M1 recovery proof and a paused-editor procedure.

### v0.4.3 — Project, task, decision and daily-review workflows

Behavior: Turn an idea into one structured project note, then update tasks and results through approved proposals.

Components: Reuse agents/emuru/SOUL.md, existing fixtures and inference qualification cases. Add only compact trusted workflow guidance/templates where needed.

Decisions:

- Project note contains existing metadata conventions: title, type, project, tags, updated, summary.
- Include goals, tasks, decisions, results and next actions. Stable block IDs support links and targeted status changes.
- Use ordinary Markdown checkboxes; record additional task status beside the task. No Kanban database.
- Search/open existing projects before proposing creation. Exact existing paths and repeated request identities return existing proposals/results.
- Similar names require clarification. Semantic duplicate detection remains advisory; approval prevents silent creation.
- Inbox promotion creates a linked project while retaining the source capture. No destructive move.
- Daily planning reads current notes and cites paths. Separate recorded facts from suggestions; do not infer deadlines.
- Adapt useful patterns from project, task, decision and review playbooks. Exclude vault-supplied instructions, automatic boards, scheduled work and inferred commitments. Pin copied material and preserve its license notice.

Acceptance/tests: Synthetic idea/project/task/update sequence; stable links; repeated task/result requests do not append duplicates. An existing-project decision/task/result update resolves and opens the target, returns a grounded anchored proposal with actual paths/block IDs (exact text for older untagged notes), and explicitly states that no update was applied. With no registered proposal capability or an unapproved target root, return an unstored text draft; never substitute a new Inbox decision note or project version. Intentional Inbox capture remains supported. Injection fixtures cannot authorize application or expand roots. Daily answers cite actual open notes. Manual synthetic conversation checks usefulness.

Risks/gates: Model-generated proposals can be wrong; deterministic validation and owner preview remain mandatory. No production gate blocks synthetic work.

### v0.4.4 — Fresh retrieval after external edits

Behavior: The next retrieval sees completed external changes without restarting containers.

Components: Reuse indexer.py, existing FTS/graph publication and indexer/MCP tests.

Decisions:

- Compare allowed-note content fingerprints before indexed reads; reuse full rebuilding when content changes.
- Include additions, deletions and renames. Validate fresh paths before returning indexed content.
- Serialize refresh with mutations. On unstable scans or refresh failure, report unavailable/stale retrieval rather than claiming freshness.
- Rebuild derived outputs after interrupted publication; Markdown remains authoritative.
- Benchmark representative synthetic vaults against the existing 15-second MCP timeout. Do not add a watcher, semantic engine or incremental framework without evidence.

Acceptance/tests: Create/edit/delete/rename externally; next search/map/neighbors reflects changes. Include same-size edits with preserved timestamps, private-root symlinks and interrupted rebuilds. Manual Obsidian smoke test follows operator approval.

Risks/gates: Full scans cost time; benchmark before activation. Shared-vault selection removes synchronization scope. Separate devices require a new Git/Syncthing conflict-and-restore assessment.

### v0.5.0 — Telegram integration and end-to-end acceptance

Behavior: Owner receives a final proposal preview, explicitly applies it, and gets an accurate durable outcome.

Components: Extend telegram/native.py, worker.py and queue integration narrowly. Update profile tool allowlists, readiness checks, qualification fixtures, container checker and affected CI tests.

Decisions:

- Bind proposals to authenticated owner, originating durable request and target vault.
- /apply requires an active claim and explicit confirmation that other writers are paused. Recheck policy and revision at application.
- Preserve final-only responses, FIFO, native history, owner-private admission and unknown-send handling.
- Repeated update IDs and repeated proposal application reuse receipts. Exact repeated requests surface prior proposals/results; intentional repetition requires a new explicit proposal.
- A crash after publication but before Telegram acknowledgment never reruns the model or mutation. Report recovered effect status separately from delivery status.
- CLI broader writes use the same proposal/application boundary; no alternate direct writer.
- Requalify changed tool/workload fingerprints. Old model qualification must not certify the expanded workload.

Acceptance/tests: Exercise all requested scenarios through real stdio MCP and pinned native synthetic runtime. Add SIGKILL, duplicate delivery, lost acknowledgment, container recreation and restored-state tests. Run targeted pytest, Ruff, native contract checks and disposable Compose acceptance.

Risks/gates: Telegram delivery cannot be guaranteed exactly once. Real Telegram/vault smoke tests require explicit approval and closure of applicable v0.4.0 deployment gates.

## 4. Acceptance, rollout and rollback

Release acceptance must demonstrate:

1. Telegram idea becomes a linked project with tasks; a later task update preserves those links.
2. Existing notes retain unrelated human content and frontmatter.
3. Stale previews fail without modifying the note.
4. Repeated requests/application do not create duplicate effects.
5. Post-write crashes recover without mutation replay.
6. Private, unauthorized, traversal, symlink and special-file attempts fail.
7. External edits become searchable.
8. Backup/restore and container recreation preserve history and uncertain-effect handling.
9. Daily planning cites actual vault data.

Roll out synthetic-only first. Then obtain approval for stopped backup/restore validation and narrow real-root enablement.

Rollback closes write admission, drains Compose and preserves the newest vault, receipts and history. Disable broader tools without deleting notes. Rebuild indexes as needed. Never restore an older queue over newer effects.

Restoring an older backup requires reconciliation before intake: effects newer than the backup may exist elsewhere. Old approval commands and uncertain work must remain quarantined.

## 5. Approval boundary and first task

Plan approval accepts the MCP authority, private recovery journal, preview/apply interface and selected single-note workflow. Shared vault and exclusive edit windows are already confirmed.

Real-vault roots, production activation and any future external synchronization require separate operator approval.
