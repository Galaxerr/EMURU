# v0.5.0 — Cloud-primary-only, Docker-only release

## Scope and decisions

The owner approved this finalization scope and confirmed all 24 manual cloud-primary
acceptance tests passed on 2026-10-19. The current release matrix is
[docs/releases/v0.5.0-acceptance.md](../releases/v0.5.0-acceptance.md).

- Support only Docker runtime and Docker-to-Docker rollback.
- Permit one authenticated cloud-primary attempt. Fail safely on upstream errors,
  incomplete results and invalid tool arguments. Never dispatch a local model
  automatically, including when a valid qualification record exists.
- Defer live local qualification and qualified-local acceptance to a future release.
  Keep qualification code, selection functionality, model identities, context,
  evidence validation and original thresholds unchanged.
- Preserve owner-bound previews and approvals, stale-write protection, durable
  mutation intent, request deduplication, receipts and crash recovery.
- Preserve all existing private histories. Remove superseded plans and obsolete
  release reports from active documentation; retain their evidence in Git history.
- Keep the competing-poller transition guard. Do not support starting or rolling
  back to a systemd runtime.

## Implementation and validation

1. Gate automatic local fallback off in shared routing policy; update primary
   readiness and status without weakening cloud destination or credential checks.
2. Extend the pinned proxy fixture to prove timeouts, rate limits, connection
   failures, upstream errors, cancellation and malformed output cause zero local
   dispatch with valid, missing and invalid qualification evidence.
3. Add explicit rollback selection of a retained content-addressed source/image.
   Require image identity, matching orchestration/runtime pins, cloud-only policy,
   exact supported schemas and matching managed profile/guidance. Refuse builds,
   schema downgrades and implicit state replacement during rollback.
4. Exercise rollback in disposable Docker state after newer effects exist. Keep
   the newest vault, profile/history, queue, receipts and mutation journal. Reject
   incompatible targets without overwriting state.
5. Record owner-confirmed results separately from independently recovered evidence.
   Use read-only snapshots for private database checks and redact private content.
6. Run affected tests, full regression, Ruff, pinned Hermes contracts, deterministic
   qualification fixture and available disposable Docker acceptance. Report actual
   results and unavailable evidence; synthetic checks never certify live model quality.
   Give host regressions one CI owner. Run pinned native acceptance once per
   disposable pass, then validate each wake target's profile while retaining all
   restart, drain, update, rollback and newest-state recovery scenarios. Reuse
   content-verified application images without changing infrastructure digest pins.

## Current acceptance criteria

- All 24 manual cloud-primary tests are owner-confirmed PASS. These include the nine
  original workflow requirements: project creation/update, byte preservation, stale
  rejection, no duplicate effect, crash recovery, authorization/injection rejection,
  external freshness, state preservation and grounded daily planning.
- Automated security, authorization, mutation and recovery regressions pass.
- Cloud failures produce no local inference and no automatic replay.
- Docker rollback preserves newest compatible state; absent or incompatible verified
  images block rollback. An old backup is never the rollback state source.
- Production candidate identity, hosted CI, operational backup/restore proof and
  target-host drain/reboot/manual-wake acceptance remain separate release gates.
  Owner-confirmed Docker restart does not independently establish a host reboot
  drill. Local qualification is not a v0.5.0 gate.

## Approval boundaries

This scope authorizes local edits and disposable validation only. No production
stop, migration, policy change, deployment, push, merge, tag or publication is
approved. Production operations require a separate approval identifying exact
images, affected state, downtime, durable stopped backup and tested recovery path.
