# v0.5.0 — Owner-approved vault editing and production acceptance

## Summary

Complete Telegram integration around the existing mutation backend. Update production documentation and validate all nine acceptance scenarios.

Current baseline: clean 6ccac9a working tree, v0.4.4 functionality, package version 0.3.4. Broader writes remain synthetic-only. Production readiness and fallback qualification remain unproven.

Delivery has two stages:

1. Implementation ready: local code, documentation, and synthetic acceptance complete.
2. Production accepted: hosted CI and target-host acceptance complete after operator approval.

Stage one may be delivered separately. It must not be labelled production accepted.

## Implementation

### Mutation authority and durable identity

- Retain the existing MCP backend, journal, filesystem checks, shared lock, atomic publication, and recovery protocol.
- Replace the /tmp-only production restriction with explicit private policy activation tied to the selected vault. Missing, malformed, or disabled policy denies broader writes.
- Approved production roots: 10_Projects, 20_Areas, and 30_Resources. Preserve existing private, generated, traversal, symlink, hard-link, and special-file denials.
- Bind each proposal to authenticated owner, bot, originating durable request, target vault, payload, and expected revision.
- Supply authenticated request context through the trusted adapter/backend boundary. Model-generated arguments cannot establish owner identity or application authority.
- Extend the existing private journal for request bindings and delivery records. Migrate additively; preserve existing receipts and history. Legacy unbound proposals cannot become production approvals.
- Keep one-note creation and exact anchored updates. No deletion, rename, automatic merge, or multi-note transaction.

### Telegram commands and previews

- Add /apply <proposal-id> writers-paused, /cancel <proposal-id>, and /propose-new <request> to admission, command handling, help, and native contract tests.
- Execute apply/cancel through deterministic operator handlers after owner-private admission and durable claim. Never invoke the model for application.
- Bare /apply explains the required confirmation and performs no mutation.
- Generate final previews from validated stored proposals. Include proposal ID, target path, revision, and exact creation content or anchored changes.
- Split long previews into numbered final messages. Show approval instructions only after all preview parts succeed.
- Record preview delivery against its approval digest. Failed or uncertain preview delivery blocks application until an explicit request successfully presents the complete preview.
- Preserve FIFO, final-only output, native conversation history, bounded turns, and existing unknown-send handling.

### Repetition and recovery

- Deduplicate exact mutation-request text within authenticated owner/bot/vault scope, across Telegram update IDs, /new, and restarts.
- Retain bindings independently of Telegram receipt pruning. Repeated mutation requests return prior proposals or outcomes without another mutation-producing model turn.
- Keep ordinary read-only questions fresh; do not cache daily planning answers indefinitely.
- /propose-new creates a fresh request identity. Duplicate delivery of that command still reuses its identity.
- Recheck policy, owner binding, preview digest, paused-writer confirmation, and revision at application.
- Persist application linkage before publication so startup recovery can identify the effect after a crash.
- Report mutation outcome separately from Telegram delivery outcome. Preserve applied, index_pending, not_applied, and quarantined semantics.
- Never replay interrupted model turns or prepared mutations. Repeated application returns its durable receipt.
- Make CLI broader writes use the same preview, approval, policy, and recovery boundary. Keep application unavailable as a model tool.

### Runtime and qualification

- Update MCP registration, profile allowlists, inference guards, readiness checks, and container checks together.
- Expose vault_propose only under the selected mutation policy. Disabled deployments retain their existing capture/read behavior.
- Extend actual live qualification workloads with project creation, anchored task updates, stale proposals, repeated requests, grounded daily planning, and injection resistance.
- Change qualification fingerprints so existing records cannot certify the expanded workload.
- Preserve configured models: cloud gemma4:31b and local qwen3.5:2b-q4_K_M. Preserve qualification thresholds and context settings.
- If either model fails qualification, block production acceptance. Do not silently substitute models or weaken requirements.
- Preserve the Hermes pin, Compose persistence, manual startup, restart: "no", and existing timeout/drain settings.

## Production rollout and approval boundaries

Use the current machine, existing Docker Compose deployment, and selected real vault.

1. Prepare locally; do not push, merge, tag, or publish. Request separate push approval when hosted CI validation is ready.
2. Inventory actual images, source mounts, persistent volumes, permissions, model digests, pollers, and host/container history.
3. Reconcile divergent receipts and native history before replacing state. Ambiguous divergence blocks cutover.
4. Present one production approval package: exact candidate, checks, affected roots, downtime procedure, backup destinations, restore drill, smoke tests, and rollback commands.
5. After approval, pause editors and intake, drain services, and create verified stopped backups.
6. Restore into isolated directories. Verify checksums, permissions, history, receipts, and uncertain-effect handling before activation.
7. Qualify the expanded workload on the actual container runtime and target hardware. Verify model-cache persistence and failover.
8. Deploy the exact candidate with hosted CI passing. Require fresh READY and approved owner-private Telegram preview/apply/readback checks.
9. Verify external-edit retrieval, recreation, drain, reboot/manual startup, and rollback readiness. Retire the old systemd path only after successful cutover.

Rollback closes broader-write admission, drains services, and preserves the newest vault, receipts, and history. Never overwrite newer effects with an older queue or backup.

Production acceptance requires every applicable gate to pass. Staged delivery leaves remaining gates explicitly pending.

Not checked during planning: test execution, hosted CI, live inference, backup restoration, or real Telegram mutations.
Known limits: exclusive editor windows remain mandatory; Telegram delivery cannot be guaranteed exactly once.
