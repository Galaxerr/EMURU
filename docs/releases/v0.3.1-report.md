### Changes

| Area | v0.3.1 result |
| --- | --- |

| Organization | `src/emuru/{vault,telegram,hermes,models}/`, `scripts/hermes/` and `scripts/service/`; all active imports, launch paths, CI and service template updated |
| Tests | Shared synthetic helpers and compact interface checks retained; deterministic worker adapter plus installed-native guards/session regressions, real SQLite and actual stdio MCP |
| Documentation | Concise architecture map, revised README/runbook/policy and refreshed synthetic notes; v0.3.0 evidence archived below |

### Upgrade and compatibility

Stop and drain work, back up the private profile and vault, then synchronize the
locked environment. Reinstall the policy, reapply the vault profile, and
reinstall/reload the user service so persisted MCP and service paths use
`scripts/hermes/`. No old-path shims are provided. Preserve queue receipts and
native history; the refactor does not change queue schema or upstream contract
pins. Follow the [runbook](../RUNBOOK.md#upgrade-to-v031).

Vault refresh provides exception rollback, including interrupted execution;
it is not a crash-atomic multi-file filesystem transaction. Startup rebuilds
derived indexes. If a failed write reports a committed path, inspect it and
repair the index rather than repeating the write. At-most-once Telegram dispatch
does not guarantee exactly-once external effects or message delivery.

Two opt-in live tests remain skipped unless explicitly enabled. Live provider
attempt counts, real-vault migration, installed service update and new owner
Telegram acceptance have not been measured for v0.3.1. Automatic synchronization,
general vault cleanup, physical remote wake and provider fallback remain outside
scope. The v0.3.0 nonblocking warning record remains historical evidence.

See [README](../../README.md), [architecture](../ARCHITECTURE.md) and
[operating runbook](../RUNBOOK.md).

### Reliability details and attempt counts

- Duplicate persistence: a repeated update remains suppressed after database
  reopen. A process exiting after durable staging preserves queued input.
  Recovery changes started work to interrupted, retaining a one-attempt notice;
  a crash during reporting cannot resend the notice or replay the original turn.
- Crash after write: the deterministic fake agent performs two turns and four
  real stdio MCP tool calls: search/open, then one Inbox write and one confirming
  search. `00_Inbox/telegram-memory.md` contains `TELEGRAM_MEMORY_742` once.
  Reopen plus duplicate replay adds **zero turns and zero MCP tool calls**;
  the write count stays **one**, with **one** uncertainty report. Protected
  synthetic notes remain unchanged. There are **zero real provider HTTP calls**
  in this test.
- Backlog order: fresh inputs are claimed in insertion/batch order, including
  decreasing update identities. The delayed first native turn completes before
  the second starts; the two texts are never merged. Exactly 86,400 seconds of
  age is accepted; 86,400.001 seconds and older are rejected/expired. Future
  clock skew is bounded at 300 seconds. Current authorization is checked again
  before dispatch. These are injected-clock synthetic results.
- Returned provider/tool failures: each tested failure permits one fake-agent
  attempt, then a terminal failed receipt; replay adds no attempt. Unknown
  egress outcomes permit one network-send attempt and block native fallback
  resends. Profile tests reject retries, recovery cycles, fallback, broader MCP
  registration, broader Telegram toolsets and Tool Search re-enablement.
- Installed `--check`: **zero provider attempts and zero MCP tool calls**;
  it checks bot identity/webhook state without polling or writing notes.
  Actual owner-message provider/MCP attempt counts remain **unmeasured**.
- Recovery rule: queued work can resume. Started work with uncertain effects
  must be reported without replay, especially after a possible Inbox write.
  An interrupted executor retires the worker until the gateway process restarts.
  Never clear the queue or retry a write to manufacture a passing checkpoint.

`TELEGRAM_CONTEXT_742` is a safe marker for future recorded restart checks, not
a claim that the owner's supplied live report used that exact marker.
