## Delivered behavior

v0.5.8 adds dependency-aware continuation of existing projects. Read-only
inspection reconciles task blocks, native cards, reviewed results and capture
receipts. Explicit owner binding supports legacy anchors, repeated requests reuse
existing state, and approved rescoping retains history.

Owner-approved batches reserve bounded cumulative allowances. Execution remains
serial, with one active coder and one independent review at a time. Successors
consume verified predecessor artifacts and require valid admission. Failed or
rejected prerequisites block dependent work. Continued results use the existing
same-note approval path. Pending capture remains distinct from applied progress,
and restart reconciliation preserves history without replay. See the
[operator runbook](../RUNBOOK.md#continuation-inspection-and-binding-v058-ticket-01)
for controls and recovery.

## Approved authority and persistence contracts

Inspection is read-only. Binding requires owner approval, including confirmation
of exact anchors when legacy task identity is ambiguous. Admission requires an
approved batch, an exact single-task grant and explicit operator dispatch.
Schema 4 binds successor inputs to predecessor grants, evidence, receipts and
final artifacts. Continued capture uses the existing guarded proposal journal.

## Lifecycle and recovery

Hold drains the admitted stage and fences later admissions. Continue preserves
charged allowances. Cancel uses the existing stop controls, and reconciliation
preserves uncertainty until stop is proven. Recovery joins persisted state
without launching work. Existing profiles require the stopped schema upgrade and
rollback procedure in the runbook.

## Inherited supervision and resource limits

### Resource qualification and limits

| Resource | Retained ceiling/boundary |
| --- | --- |
| Enrollment | 24 hours, monotonic and boot-bound |
| Stable project | One Scout, two coders/two reviewers; 1,920 reserved seconds; original coder/reviewer loop 1,800 seconds |
| Stage time | Coder 600 seconds; reviewer 300 seconds; Scout at most 120 seconds |
| Iterations/checks | Coder 12 and reviewer 4 per stage; loop 24/8; four checks per coder/eight per loop, 60 seconds per check |
| Captured output | 64 KiB per check/reviewer; 256 KiB per coder; 640 KiB loop total |
| Artifacts | 8 MiB per coder, 17 MiB loop; Scout report 64 KiB |
| Reviewer | Complete input 256 KiB; output 64 KiB; strict verdict 32 KiB; no truncation to fit |
| Selected files | 100 committed UTF-8 files, 256 KiB each, 2 MiB total |
| Worker/check OS | One CPU, 512 MiB, 64 PIDs; fresh 64 MiB/1,024-inode scratch; no board/vault/socket/credentials/network in checks |
| Supervisor metadata | 1 MiB including 4 KiB emergency restriction reserve; 4 KiB receipt, 3,500-character added status projection |
| Provider usage | Observational outside the explicitly bounded qualification runner; missing usage is unavailable, not zero or a spend guarantee |

Reservations are durable, charged before claim and never refunded after crashes or
cancel. Boundary tests use injected clocks/narrowed limits plus actual native
claim/process/refusal checks; they do not claim every maximum was consumed.

Batch reservations add a cumulative boundary and execution remains serial.
