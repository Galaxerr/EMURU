## Delivered behavior

An authenticated private-owner request names an exact applied spec proposal,
native task and independent review run. The capture path reopens the actual
verified completion, reads the current canonical project note and prepares one
deterministic anchored update. It does not start coding or write a note.
A separate authenticated approval of the complete preview, with external writers
paused, is required before the existing mutation path can apply it.

The result is inserted beneath one exact existing task line. Its checkbox, stable
block ID, whitespace and unrelated sections are preserved. Missing or ambiguous
anchors require explicit selection; no new section or duplicate project note is
created. The formatter uses validated identifiers and fixed factual wording:
task/run bindings, evidence/diff digests, verified fixed-check ID/result,
qualification limits and next action. It embeds no raw logs, task/model prose,
credentials or arbitrary filesystem paths.

Current coding uses selected-file workspaces and artifact/diff provenance, without
a task Git checkout, branch or result commit. A repository baseline SHA identifies
input only and is never labeled a result commit. The summary explicitly names
`python_unittest`; passing fixed Monty cases does not prove native unittest
completion, native/Monty equivalence or general correctness.

| `src/emuru/projects/{coder_board,coder_runtime,reviewer,rework}.py` | Native task/run authority and immutable coder/reviewer/lineage evidence reopening |

## Approved authority and persistence contracts

- **H1 — capture evidence versus current note:** capture verifies immutable
  approved spec, grant, native runs/events and coder/reviewer artifacts against
  execution identities, while separately validating current owner/vault policy
  and fresh target revision. A later note edit does not erase historical code
  evidence. Current source/image/catalogue/repository guards remain required;
  execution and rework authority are never renewed by capture.
- **H2 — one authoritative journal:** additive `project_result_captures` metadata
  lives in the existing mutation journal. Each canonical completion key includes
  owner/bot/vault/project/spec/task, coder/reviewer runs and grant/evidence/diff/
  packet/outcome digests. Monotonic generations bind the original authenticated
  request, exact proposal, target revision, anchor and formatter version. Mutable
  note revision is separate from completion identity. A unique active-generation
  index prevents concurrent duplicate proposals. Proposal and linkage commit in
  one transaction under the existing vault writer lock; receipts own apply facts.
- **H3/H4 — reverify before first write:** the existing apply path invokes a
  read-only pinned-runtime subprocess before initial capture publication. It has
  a 30-second deadline, bounded request/response, minimal environment, no model
  tools, credentials or mutation authority. Failure refuses application.
  Applied/prepared/index-pending receipt recovery remains receipt-first; it never
  reruns a worker or fabricates historical evidence.

Capture bindings, anchors and generated result detail are each limited to 4 KiB;
cumulative logical capture metadata is limited to 1 MiB per profile. Overflow is
refused without truncation, history deletion or use of supervisor emergency space.
Old profiles require the explicit stopped-profile upgrade with a preserved backup;
startup does not silently migrate them. Unsupported/inconsistent newest metadata
refuses without deletion; an old executor cannot strip it to permit rollback.

## Lifecycle and recovery

| Observation | Required outcome |
| --- | --- |
| Verified code without owner capture request | Ready for capture; no proposal or note write |
| Duplicate/concurrent capture or lost preview acknowledgement | Same pending proposal or terminal receipt, without rebinding its original request |
| Rejected/expired generation | Note and code evidence preserved; only fresh authenticated `capture-new` can request another generation |
| External edit after preview | Stale refusal; preserve current bytes and require fresh preview/approval |
| Changed/missing/rejected/uncertain evidence | No new qualifying capture or first write |
| Crash before proposal/link transaction commit | Neither orphan proposal nor capture addition |
| Prepared write with expected after bytes | Recover receipt/index state only; do not republish |
| Prepared write with original before bytes | `not_applied`; no automatic retry |
| Neither before nor after bytes | Uncertain/quarantined; preserve state for investigation |
| Saved note with `index_pending` | Recover derived indexing only, without changing note bytes/mtime |
| Applied receipt followed by human edits or unavailable old artifacts | Preserve historical application; no automatic restoration, recapture or execution |

## Inherited supervision and resource limits

coding, M5 independent review/single rework and M6 supervision remain supported.
Enrollment/status/hold/continue/cancel launch nothing. Explicit grants and operator

reconciliation never retries work. Sleep fences admission before checking active

## Remaining limits and future decisions

Full native model-driven check generation, native/Monty equivalence and optional
live Ollama conversation gates remain unverified. Fixed Monty cases and bounded
disposable-task evidence do not establish universal correctness or production
certification. Groq Free-plan/global-ZDR status was owner-attested, not independently
console-audited. Authorized selected source can reach the approved cloud provider;
there is no source-confidentiality guarantee or automatic local fallback. The
inherited SQLite DELETE-journal fallback is retained; concurrent WAL durability
is not certified. Normal service was restored inactive, locks released and queues
drained after qualification; no production vault was changed.

M8 dependency-aware multi-task continuation is implemented and technically
qualified. See the [v0.5.8 release and acceptance record](v0.5.8-implementation.md).
M9 full integration remains on the [roadmap](../plans/EMURU-v0.6.0-implementation-plan.md). Local Git execution and
controlled GitHub operations are separate future capabilities without assigned
versions or a selected credential technology. Approved design constraints survive
the retired planning documents: enroll a trusted repository/exact baseline and
isolated branch; keep credentials in a trusted service outside workers/tests;
require tests and independent review bound to the final tree/commit before push/PR;
persist remote intent and reconcile external receipts before any retry. New
repositories default private; public creation and later visibility changes require
explicit authority. One authenticated request may explicitly bundle independently
bounded scopes, but omitted operations remain denied. Merge, deletion and release
publication require separate authorization. These are design constraints, not
implemented features or execution grants.

Permanent-host provisioning, encrypted stopped backup/restore, migration, cutover
and reboot certification remain in the [deployment backlog](../deployment-backlog.md).
No merge, tag, deployment, release publication or activation follows from M7 GO.
