## Persistence and transaction boundaries

One board lives at `<profile-home>/emuru-projects/kanban.db`, beneath the existing
persistent private profile mount. Directory mode is 0700; DB/binder/init-lock
files are 0600. Paths and SQLite sidecars reject symlinks and hard links.
Native SQLite owns schema, state, events and dependency records. Native card
bodies hold schema-1 spec receipt, approval digest, revision and task bindings;
the tenant key binds owner, bot, selected vault and canonical path. No extra
binding database, copied transcripts, scheduler or execution grant is introduced.

Each native card creation commits independently. A binder flock serializes
multi-card retries; stable project/revision/task keys reconcile partial creation.
Archived cards remain authoritative and are never recreated automatically.
Status reports partial sets, stale notes and cards belonging to another revision.
There is no cross-vault/Kanban transaction and no claim of verified code completion.
Older applications ignore this new directory; newest state must remain intact.
No native pin/schema migration or destructive rollback is introduced in M2.

including task anchors, indentation, planned checks and the single specification
identity. Its regression substitutes the published example and checks both the
unchanged renderer and M2 parser. `src/emuru/projects/spec.py` is byte-identical

Issue B is closed for acceptance: the owner explicitly reconfirms repeated `/new`
works and history survives. Earlier diagnostic notes identify stale text-request
deduplication and session transitions followed by optional reset failures. Existing
regressions cover those paths. The branch additionally fixes a demonstrated guard
defect: failed or cancelled `sendChatAction` latched the turn as failed even though
it is only a typing indicator. Regression coverage asserts an actual reset and its
success reply, not merely bot startup. Ordinary message-delivery failures retain
the no-retry fence. The exact exception behind every historical report cannot be
reconstructed from supplied evidence; no remaining repeated failure is reported.

Issue C remains an environmental observation, not an application release blocker:
recorded TCP/HTTPS probes demonstrate intermittent Telegram connectivity outside
