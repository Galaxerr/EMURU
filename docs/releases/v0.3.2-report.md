# v0.3.2 Docker foundation report

## Scope and baseline

Baseline: clean `main` at `b10c2fb6c110516a0a6aaea7235afcdf7493dcdb`.
Implementation: uncommitted worktree on `feat/v0.3.2-docker-foundation` based on
that commit. No vault content, model cache or systemd unit was migrated. The
root `.env` now holds source credentials; initialization refreshed only the
private runtime copies. The directory migration later stopped and restored the
three already-running production containers, including their existing poller.

The operator setup seam is provided by `scripts/hermes/container.py`: it
generates the private deployment directory, gateway key, validated route copy,
LiteLLM configuration and Compose environment. Manual model selection remains
explicit; initialization does not pull weights or reuse the host cache.

Container data defaults to `$HOME/.local/state/emuru/container`. Generated
Compose metadata is `infra/docker/deployment.env`, contains paths and IDs only,
and remains mode 0600 and ignored by Git. The launcher creates private state
directories before builds and keeps existing history, receipts and Ollama data.
The former in-checkout directory was moved intact; readable-file checksums and
protected-file inode metadata verified 426 unchanged entries before restart.
The application image was rebuilt and all three services recreated with the new
bind paths. Ollama and LiteLLM became healthy; the Telegram worker reached
`required guards and five MCP tools READY`. Retained status showed one completed
receipt, five failed receipts and `provider_failed`; no new Telegram message was
sent during verification.

External provider keys, the Telegram token and the generated gateway key use the
ignored workspace-root `.env` as their source. Launch tools reject unsafe file
permissions. Container initialization writes private mode-0600 copies, passes
only the selected provider key to LiteLLM, and keeps Telegram's token in its
private Hermes profile.

The opt-in container route exposes only the selected cloud primary through the
authenticated `emuru` alias. The installed local candidate is stored with a
catalog digest and null qualification. It is not a proxy route or automatic
fallback. Existing host model selection and deployment remain operational.

Runtime policy remains zero Hermes retries/recovery cycles, empty fallback
providers, at most 12 turns, exactly five vault tools, no generic toolsets,
reference-only retrieval, final-only Telegram output, serialized execution and
uncertain-effect protections. Queue/index/native Telegram semantics are unchanged.

## Persistence evidence and acceptance gaps

Application containers were removed/recreated around the same private binds.
A valid disposable `queued` receipt was created through `TelegramQueue.stage`,
then read through SQLite read-only mode and compared alongside profile, policy
and synthetic history hashes. No live worker, recovery or pruning was invoked.
Status reported one queued receipt and no health errors after recreation.

The independent Ollama cache had no models. Real daemon recreation preserved the
empty inventory. No weights were downloaded or copied from an active host cache.
Model-digest persistence therefore remains an explicit acceptance gap.

systemd cutover are not included. Full live deployment acceptance is not claimed.
